# Wire protocol, version 1

This document is the contract between the `airon` Python SDK (this repository) and an Airon server.
Both sides follow it. Where the two disagree, this document wins; open an issue or a pull request to
change it.

Conventions

- Bodies are JSON, UTF-8. Request bodies larger than 1 KiB should be gzip-compressed with
  `Content-Encoding: gzip`.
- Timestamps are Unix seconds as floats, UTC.
- Unknown fields must be ignored by both sides, so the protocol can grow without breaking old clients.
- Metric names are hierarchical with `/`, at most 200 characters, for example `train/loss`.
- JSON cannot carry `NaN` or infinity. A metric value that is not finite is sent as the string
  `"NaN"`, `"Infinity"` or `"-Infinity"`. The server records it (it is a signal worth showing) and
  leaves it out of charts.
- The examples use `https://airon.example.com`. The SDK has **no default server**: the address always
  comes from `AIRON_URL` or `airon login`.

## Authentication and versioning

- `Authorization: Bearer <api key>` on every request. Keys never appear in URLs or bodies.
- `401` invalid or revoked key. `403` the key may not log runs (read-only or wrong scope).
- Clients send `X-Airon-Protocol: 1` and `User-Agent: airon/<sdk version> python/<python version>`.
  Servers answer with `X-Airon-Protocol: 1`. A server that cannot speak the client's version answers `426`.

## GET /v1/ping

Used by `airon doctor` and `airon login` to check the address and the key.

```json
{"ok": true, "protocol": 1, "key": {"name": "pod-h100", "scope": "tracker"}, "server_time": 1730402880.1}
```

## POST /v1/runs: create or reopen a run

Idempotent by `run_id`, so a retried request is harmless. The client generates `run_id` (a UUID4 string).

```json
{
  "run_id": "6f1c1c0e-3f55-4d66-9a8e-2f0f0d8f0b11",
  "project": "memory-layer",
  "name": "baseline-v2",
  "experiment": "Baseline v2",
  "config": {"lr": 3e-5, "batch_size": 32, "model": {"name": "small-encoder"}},
  "env": {
    "python": "3.11.6",
    "platform": "Linux-5.15-x86_64",
    "host": "pod-8c1f",
    "cloud": "runpod",
    "gpus": [{"index": 0, "name": "NVIDIA H100 80GB HBM3", "mem_total_mb": 81559}],
    "git": {"commit": "5d1e0aa", "branch": "main", "dirty": false, "remote": "git@example.com:acme/model-code.git"},
    "libs": {"torch": "2.5.0", "numpy": "2.1.0"}
  },
  "total_steps": 50000,
  "total_epochs": 5,
  "tags": ["baseline"],
  "notes": "",
  "resume": "never",
  "started_at": 1730398080.0
}
```

Only `run_id` and `project` are required. Everything else is optional. `name` is generated by the server
when missing. `experiment` is the title of an Airon experiment to link the run to; if there is none, the
server ignores it and says so in `warnings`. `resume` is `"never"` (default), `"allow"` or `"must"`.

| Situation | Result |
|---|---|
| `run_id` is new, `resume` is not `"must"` | `201`, a new run |
| `run_id` exists and the run is still running | `200`, an idempotent update (covers retries) |
| `run_id` exists and is finished, failed, killed or crashed, `resume` is `"allow"` or `"must"` | `200`, reopened, `resumed: true` |
| `run_id` exists and is over, `resume` is `"never"` | `409` |
| `run_id` is new and `resume` is `"must"` | `404` |

```json
{"run_id": "6f1c…", "name": "baseline-v2", "url": "https://airon.example.com/runs/6f1c…",
 "status": "running", "resumed": false, "last_step": null, "last_seq": 0, "warnings": [],
 "server_time": 1730402880.2}
```

`last_step` and `last_seq` let a resumed run continue where the server stopped: the client starts `seq`
after `last_seq`.

## POST /v1/runs/{run_id}/events: send a batch

```json
{"events": [
  {"seq": 41, "t": 1730402880.0, "step": 12400, "epoch": 1.98,
   "metrics": {"train/loss": 0.412, "lr": 2.4e-5}},
  {"seq": 42, "t": 1730402880.0, "system": {"gpu0/util_pct": 96, "gpu0/mem_used_mb": 71234, "cpu/util_pct": 38}},
  {"seq": 43, "t": 1730402881.0,
   "progress": {"step": 12400, "total_steps": 50000, "epoch": 1.98, "total_epochs": 5,
                "steps_per_sec": 2.4, "samples_per_sec": 76.8, "tokens_per_sec": 18200}}
]}
```

At most 500 events and 1 MiB (uncompressed) per request.

Every event has `seq` (integer, increasing by 1 per run, assigned by the client) and `t`. The server
ignores an event whose `seq` it already has, which makes retries safe. An event can carry any of these
keys, several at once:

| Key | Content |
|---|---|
| `metrics` | `{name: number}` at an optional `step` (integer) and `epoch` (float, may be fractional) |
| `system` | `{name: number}` hardware samples, kept off the step axis (see well-known names) |
| `progress` | `step`, `total_steps`, `epoch`, `total_epochs`, `steps_per_sec`, `samples_per_sec`, `tokens_per_sec`, all optional |
| `log` | `[{"stream": "stdout" or "stderr", "text": "one line"}]` console lines |
| `checkpoint` | `{"uri": "hf://org/repo@rev", "step": 12000, "label": "best", "metrics": {}}` a pointer, never the file |
| `summary` | `{name: any JSON}` values set explicitly by the user |
| `config` | `{...}` merged into the run's config, key by key |

An event with only `seq` and `t` is a heartbeat. The server derives these without help: the ETA (from
the recent progress rate, so pauses for evaluation and checkpoints are included), the best and last
value of each metric, and the `crashed` state (no event for 5 minutes while still `running`).

Response `200`, even when some events were refused, so one bad event cannot block the queue:

```json
{"accepted": 3, "duplicates": 0, "last_seq": 43, "rejected": []}
```

A rejected event looks like `{"seq": 44, "reason": "metrics.train/loss is not a number"}`. The client
must not resend rejected events.

Errors: `401`, `403`, `404` unknown run, `413` body too large (the client splits the batch and retries),
`422` malformed request (not retried), `429` with `Retry-After` (seconds), `5xx`.

## POST /v1/runs/{run_id}/finish

```json
{"status": "failed", "t": 1730412345.0, "exit_code": 1,
 "error": {"type": "torch.OutOfMemoryError", "message": "CUDA out of memory…", "traceback": "Traceback (most recent call last):\n…"},
 "summary": {"eval/loss.best": 0.431}}
```

`status` is `"finished"`, `"failed"` or `"killed"` (for example a terminated pod). Idempotent. Events that
arrive after it are still recorded; the status does not change. `"crashed"` is never sent by a client:
the server sets it when a running run goes silent.

## Well-known names

These get special treatment in the interface. Everything else is shown too.

- Metrics: `train/loss`, `eval/loss`, `eval/*`, `train/*`, `lr` (or `train/lr`), `train/grad_norm`.
- System: `gpu{i}/util_pct`, `gpu{i}/mem_used_mb`, `gpu{i}/mem_total_mb`, `gpu{i}/temp_c`,
  `gpu{i}/power_w`, `cpu/util_pct`, `ram/used_mb`, `ram/total_mb`, `disk/used_gb`, `disk/total_gb`.

## Client behaviour

The SDK must follow these rules. They are what lets a team adopt it without worrying about their training.

1. **Never break training.** `log()` only appends to an in-memory queue and returns. Nothing in the
   SDK raises into user code because of the network, the server or the disk. At most one warning is
   printed per kind of problem.
2. **Bounded memory.** The queue holds at most 100,000 events. When full, drop the oldest `system`
   events first, then the oldest `metrics`, and warn once.
3. **Batching.** A background thread flushes every 2 seconds or 200 events, whichever comes first,
   sends a heartbeat every 30 seconds, and samples hardware every 10 seconds. All configurable.
4. **Retries.** Exponential backoff from 1 s to 60 s with jitter, honouring `Retry-After`. Retry on
   network errors, `408`, `425`, `429` and `5xx`. Do not retry other `4xx`: drop the batch and warn. On
   `401` or `403` stop sending, keep everything in the offline spool, and warn once.
5. **Offline spool.** Events that cannot be delivered are written to JSON lines under `$AIRON_DIR`
   (default `~/.cache/airon`), one directory per run. `airon sync` uploads what is there, in order.
   `AIRON_MODE=offline` writes only to the spool; `AIRON_MODE=disabled` makes every call a no-op.
6. **Exit.** Flush on normal exit and on an unhandled exception, waiting at most 10 seconds. An unhandled
   exception inside `with airon.init(...)` is reported as `failed` with its traceback and re-raised.
   `SIGTERM` is reported as `killed` after the program's own handler has run: chain existing handlers,
   never replace them.
7. **Console.** Capture the tail of stdout and stderr (default 200 lines) without breaking progress bars
   that use carriage returns. It can be turned off with `console=False`.

## Environment variables

| Variable | Meaning |
|---|---|
| `AIRON_URL` | Server address, for example `https://airon.example.com` |
| `AIRON_API_KEY` | The key |
| `AIRON_PROJECT` | Default project |
| `AIRON_RUN_ID` | Run to resume or attach to |
| `AIRON_MODE` | `online` (default), `offline` or `disabled` |
| `AIRON_DIR` | Where the spool and credentials live |

`airon login` stores the address and the key in `~/.config/airon/credentials.json`, readable only by the
owner. Environment variables take precedence over the file.
